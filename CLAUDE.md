# CLAUDE.md — Project context for AI assistants

## What this is

**kafka-connect-salesforce** is OSO's open-source (Apache-2.0) suite of Salesforce connectors for Apache Kafka Connect: four connectors built on Salesforce's Pub/Sub API (gRPC) and Bulk API 2.0 that replace Confluent's proprietary Salesforce connector family. Docs: https://salesforcekafkaconnector.com. Maven group `sh.oso`.

| Module | Connector class | Direction |
|---|---|---|
| `connect-salesforce-source` | `sh.oso.salesforce.source.SalesforceSourceConnector` | Salesforce to Kafka (CDC via Pub/Sub, Bulk 2.0 snapshot and polling) |
| `connect-salesforce-sink` | `sh.oso.salesforce.sink.SalesforceSinkConnector` | Kafka to Salesforce (Bulk 2.0, REST Composite) |
| `connect-salesforce-pe-sink` | Platform Event sink | Kafka to Salesforce (Pub/Sub publish) |
| `connect-salesforce-streaming-source` | Legacy CometD source | Salesforce to Kafka (orgs without Pub/Sub API) |
| `sf-core` | Shared Salesforce protocol library and the fake Salesforce test harness (`test-jar`) | |
| `e2e-tests` | Docker end-to-end tests against a real Connect worker; also generates the configuration reference | |
| `tools/confluent-migration` | `confluent2oss.py` config translator and `verify_cutover.py` | |
| `website/` | Docusaurus docs site | |

## Building and testing

```bash
mvn clean verify              # unit + integration + Docker e2e (Kafka + Connect worker)
mvn clean verify -DskipE2E    # without Docker
mvn clean package -DskipTests # plugin ZIPs land in */target/*-kafka-connect-plugin.zip
```

No Salesforce org is needed: `sf-core`'s test-jar ships a fake Salesforce (WireMock HTTP surface with the Bulk 2.0 job lifecycle, an in-process gRPC Pub/Sub API with replay semantics, and a CometD stub). CI runs on Java 17 and 21 and publishes a `migration-evidence` artefact from the Confluent cutover test on every build.

## Releasing

Conventional commits on `main` drive release-please, which maintains the release PR (version bump and CHANGELOG). Merging that PR creates the `vX.Y.Z` tag and GitHub Release; the release workflow validates the POM version, builds, deploys signed artefacts to Maven Central and attaches the four plugin ZIPs. Never tag by hand. Details: `website/docs/development/releasing.md`.

## Support and security policy (public)

- `SUPPORT.md`: the Enterprise support subscription scope, priorities, response targets (P1 60 minutes and 4-hour workaround, P2 4 hours, P3 one business day, P4 two), UK business hours with no staffed 24x7 desk, supported-version window (current and previous minor), Salesforce seasonal release readiness, and the maintenance and continuity commitments.
- `SECURITY.md`: private vulnerability reporting, two and five business-day acknowledgement and assessment, ten business days for critical and high fixes, coordinated disclosure.

Anything client-facing in this repo, including the README's Commercial Support section, must stay consistent with those two files. Do not claim 24x7 support, per-connector pricing or features that are not in a published release.

## Commercial proposals and client correspondence

Sales material lives in `sales/`, which is gitignored and must never be committed: per-client folders with the enquiry, the reply, the proposal source and the built documents, plus `sales/README.md`, the local playbook for producing a support proposal (the engagement kit, the support model, the rate card and prior art). Client-facing documents follow the OSO house style: UK English, no em dashes, no emoji, no tildes or arrow glyphs in prose, ranges written as words, inline code only for genuine identifiers.

## Conventions

- Configuration keys are `sf.*`; every property is documented in the generated reference (`website/docs/reference/configuration/*.md`), regenerated by the e2e module. Do not hand-edit those files.
- Salesforce credentials are Connect `PASSWORD` configs and are never logged.
- Prefer the fake Salesforce for new tests; e2e tests that need Docker are in `e2e-tests`.
